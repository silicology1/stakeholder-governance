### 1. How the Upgrade is Done (Contract Logic)
The contract implements a secure, **two-step timelocked upgrade mechanism** to prevent malicious or rushed upgrades. It relies on OpenZeppelin's `UpgradeableComponent`, which wraps Starknet's native `replace_class_syscall`.

* **Step 1: Propose the Upgrade**
  An account with `DEFAULT_ADMIN_ROLE` calls `propose_upgrade(new_class_hash)`. 
  - The contract verifies upgrades are not permanently disabled.
  - It records the `new_class_hash` and sets an `effective_at` timestamp exactly **7 days** (`UPGRADE_TIMELOCK_DURATION = 604_800` seconds) in the future.
  - It emits an `UpgradeProposed` event.

* **Step 2: Execute the Upgrade**
  After the 7-day timelock has elapsed, an account with `DEFAULT_ADMIN_ROLE` calls `execute_upgrade()`.
  - The contract verifies the timelock has passed (`get_block_timestamp() >= effective_at`).
  - It clears the pending upgrade state from storage.
  - It calls `self.upgradeable.upgrade(pu.new_class_hash)`, which triggers the Starknet syscall to replace the contract's class hash, effectively upgrading the logic while **preserving all existing storage and state**.

> ⚠️ **Important Caveat:** The contract includes a `disable_upgrades_forever()` function. If an admin calls this, the `upgrades_disabled` flag is permanently set to `true`, and any future calls to `propose_upgrade` or `execute_upgrade` will revert forever.

### 2. How to Get the `new_class_hash`
The `ClassHash` is the unique cryptographic hash of your compiled contract code on Starknet. You cannot calculate it manually; it must be generated by compiling and declaring the new code to the network. 

Here is the standard workflow to get it:

#### Step A: Compile the New Contract
Update your Cairo code and compile it using Scarb. This generates the Sierra and CASM artifacts.
```bash
scarb build
```
*This creates files like `target/dev/your_project_StakeholderConviction.contract_class.json`.*

#### Step B: Declare the Class on Starknet
You must "declare" this new compiled class to the Starknet network (Sepolia testnet or Mainnet). This does **not** deploy a new contract instance; it merely registers the new logic blueprint and returns its hash. 

You can do this using **Starkli** or **sncast**:

**Using Starkli:**
```bash
starkli declare target/dev/your_project_StakeholderConviction.contract_class.json \
  --network <sepolia/mainnet> \
  --account <your_account.json> \
  --keystore <your_keystore.json>
```

**Using sncast:**
```bash
sncast declare \
  --contract-name StakeholderConviction \
  --url <sepolia/mainnet_rpc_url> \
  --account <your_account_name>
```

#### Step C: Extract the `new_class_hash`
After the declaration transaction is accepted, the CLI tool will output the resulting `class_hash`. It will look something like this:
```text
Class hash declared successfully: 0x04a7... (your new class hash)
```
**This `0x...` value is your `new_class_hash`.** You can also find it on a block explorer (like StarkScan or Voyager) by looking up the declaration transaction hash.

In Starknet, storage is tied to the **contract address**, not the code (class hash). When you call `replace_class_syscall` (via OpenZeppelin's `upgradeable.upgrade`), you are only swapping out the *logic/bytecode* that interacts with the contract. All existing data (balances, proposals, disputes, admin roles, etc.) remains safely intact at that address.

### ⚠️ THE CRITICAL "BUT": Storage Layout Rules
While the storage *data* is preserved, the new contract code must know exactly how to read it. **If you change the storage layout in your new code, the contract will read corrupted data or fail entirely.**

To ensure a safe upgrade, you **MUST** follow these strict rules for the `#[storage]` struct in your new contract:

1. **DO NOT reorder existing variables**: The order of variables in the `#[storage]` struct determines their memory offsets. Changing the order shifts everything and corrupts the data.
2. **DO NOT change data types**: You cannot change a `u64` to a `u128`, or a `ContractAddress` to a `felt252`. The new code must expect the exact same type.
3. **DO NOT rename existing variables or struct fields**: Storage keys are generated by hashing the variable names (using Poseidon). Renaming a variable changes its hash, meaning the new code will look in the wrong storage slot and find empty/zero data.
4. **DO NOT remove existing variables**: If you no longer need a variable, leave it in the struct (you can prefix it with `_` to avoid compiler warnings, e.g., `_deprecated_var`).
5. **Adding new variables is SAFE, but ONLY at the very end**: You can append new variables to the bottom of the `#[storage]` struct. Do not insert them in the middle.

### Special Warning for Your Contract: OpenZeppelin Components
Your contract heavily relies on OpenZeppelin components:
```cairo
#[storage]
struct Storage {
    #[substorage(v0)]
    erc20: ERC20Component::Storage,
    #[substorage(v0)]
    accesscontrol: AccessControlComponent::Storage,
    // ... etc
}
```
**You must keep these component declarations in the exact same order.** If you add a new component, add it at the very bottom. Changing the order of `erc20` and `accesscontrol`, for example, would catastrophically mix up token balances with admin roles.

### What if you absolutely MUST change the storage layout?
If you need to fundamentally restructure the storage (e.g., changing a `Map` to a different data structure), you cannot do it directly. You must write a **storage migration function** in the new contract. This function would:
1. Read the data from the old storage layout.
2. Write it into the new storage layout.
3. Be called exactly once by an admin immediately after the upgrade.
*(Note: Migration is complex, gas-expensive, and prone to errors. Avoid it if possible).*

### Best Practices Before Upgrading
1. **Test on Sepolia First**: Deploy the current contract to Sepolia, populate it with dummy data (create a proposal, stake some tokens), declare the new class, and execute the upgrade. Then, call view functions to ensure the data is still readable.
2. **Use Storage Proofs**: Tools like Starkli or sncast can be used to query specific storage slots before and after the upgrade to verify the raw hex data hasn't shifted.
3. **Keep a Backup**: Always keep the exact source code and `scarb build` artifacts of the currently deployed version. 

As long as you respect the existing storage layout, the upgrade will be seamless and completely non-destructive to user data.
